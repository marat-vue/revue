# Как тестировать API с настоящей PostgreSQL?

> [!NOTE]
> Запросы Drizzle, ограничения и миграции нужно проверить на настоящем PostgreSQL. Для тестов используется отдельная база, которую можно безопасно очищать.

## Вопрос

Как тестировать Express API с настоящей PostgreSQL? Как готовить и очищать тестовую базу?

## Отдельная строка соединения

```dotenv
# .env.test
NODE_ENV=test
DATABASE_URL=postgresql://app:password@localhost:5432/app_test
```

Никогда не запускай очистку на рабочей базе. Полезна явная защита:

```ts
if (env.NODE_ENV === "test" && !env.DATABASE_URL.includes("test")) {
  throw new Error("Тесты должны использовать отдельную базу");
}
```

Имя не является абсолютной гарантией, но помогает остановить случайную ошибку. Надёжнее использовать отдельного пользователя и отдельное окружение.

## Подготовка схемы

Перед набором тестов примени те же миграции:

```bash
drizzle-kit migrate --config=drizzle.test.config.ts
```

Тестовая схема должна совпадать с рабочей.

## Очистка

```ts
import { afterAll, beforeEach } from "vitest";
import { sql } from "drizzle-orm";
import { db, pool } from "../src/db/index.js";

beforeEach(async () => {
  await db.execute(sql`TRUNCATE TABLE tasks, users RESTART IDENTITY CASCADE`);
});

afterAll(async () => {
  await pool.end();
});
```

`TRUNCATE` является разрушительной операцией. Такой код допустим только для гарантированно отдельной тестовой базы.

## Почему внешний `ROLLBACK` не всегда помогает

Тест может открыть транзакцию, но HTTP-обработчик возьмёт другое соединение из пула. Его запросы не попадут в транзакцию теста.

Варианты изоляции:

- очищать отдельную базу между тестами;
- создавать уникальные данные и удалять их;
- создавать отдельную схему или базу на запуск;
- передавать один транзакционный клиент через специально устроенные зависимости.

Для небольшого проекта проще отдельная база и явная очистка.

## Что проверить

- миграции применяются с нуля;
- уникальная почта действительно запрещена;
- внешний ключ запрещает неверную связь;
- каскадное удаление работает как задумано;
- транзакция откатывает все изменения;
- CRUD возвращает правильные данные.

## Что важно помнить

- Тестовая база отдельная, со своей строкой соединения в `.env.test`.
- Перед тестами применяются настоящие миграции — так проверяются и они сами.
- Очистку (`TRUNCATE ... RESTART IDENTITY CASCADE`) выполняют только при проверенной тестовой строке соединения.
- Внешняя транзакция с `ROLLBACK` не работает, если код под тестом берёт свои соединения из пула.
- После набора тестов пул закрывают, иначе Vitest не завершится.

## Мини-шпаргалка

- Интеграционные тесты используют настоящий PostgreSQL.
- База для тестов должна быть отдельной.
- Перед тестами применяются настоящие миграции.
- Очистка не должна иметь доступа к рабочим данным.
- Пул закрывается после набора тестов.
