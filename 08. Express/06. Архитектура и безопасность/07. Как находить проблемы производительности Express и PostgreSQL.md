# Как находить проблемы производительности Express и PostgreSQL?

> [!NOTE]
> Для обычного CRUD API узким местом чаще становится запрос к базе, внешняя служба или слишком большой ответ, а не сам Express. Сначала измеряй, затем исправляй доказанную причину.

## Вопрос

Как найти и исправить проблемы производительности Express API и запросов к PostgreSQL?

## Частые причины

- запрос без нужного индекса;
- выбор всех строк без ограничения;
- проблема N + 1;
- слишком большой JSON;
- долго открытая транзакция;
- исчерпанный пул соединений;
- синхронный тяжёлый код в обработчике;
- внешний запрос без предельного времени;
- запись огромных объектов в журнал.

## Сначала измерение

Записывай длительность HTTP-запроса и важных операций базы. Для SQL используй:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
FROM users
WHERE email = 'anna@example.com';
```

`EXPLAIN ANALYZE` действительно выполняет запрос. С изменяющими запросами в рабочей базе его применяют осторожно.

## Выбирай только нужные данные

```ts
const result = await db
  .select({
    id: users.id,
    name: users.name,
  })
  .from(users)
  .limit(20);
```

## Не блокируй цикл событий

```ts
// Плохо для большого объёма внутри HTTP-обработчика.
const result = calculateHugeReport(data);
```

Тяжёлый расчёт задержит все запросы процесса. Его выносят в отдельный поток, процесс или фоновую задачу.

## Предельное время запросов

Для `pg` можно согласовать ограничения соединения и PostgreSQL, например `statement_timeout`. Внешние HTTP-запросы нужно отменять через `AbortSignal`.

Предельное время не ускоряет операцию, но не даёт ей удерживать ресурс бесконечно.

## Кэш

Кэш полезен для часто читаемых и редко меняющихся данных. До добавления нужно ответить:

- где он хранится;
- сколько живёт запись;
- когда она удаляется;
- допустимы ли устаревшие данные;
- что произойдёт в нескольких процессах.

## Что важно помнить

- Сначала измеряют длительность запроса и SQL, а потом оптимизируют доказанную причину.
- `EXPLAIN ANALYZE` показывает, использует ли запрос индекс и где тратится время.
- Тяжёлый синхронный расчёт в маршруте блокирует цикл событий для всех клиентов.
- Списки ограничивают по размеру, а ответ — по набору столбцов.
- Кэш требует правил инвалидации, а таймауты — понятного ответа клиенту.

## Мини-шпаргалка

- Сначала измеряй длительность.
- Ограничивай списки и размер ответа.
- Проверяй индексы и N + 1.
- Не выполняй тяжёлый синхронный расчёт в маршруте.
- Предельное время и кэш требуют явных правил.
