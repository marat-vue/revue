# Асинхронный UI, waitFor, nextTick и flushPromises

> [!NOTE]
> Для ожидания появления элемента используют `findBy*`, для ожидания произвольного условия — `waitFor`. Оба повторяют проверку, пока она не пройдёт или не истечёт таймаут. Во Vue есть два уровня асинхронности: ререндер после изменения состояния (ждём `nextTick`, его уже ждут `fireEvent` и `trigger`) и промисы — запросы, `onMounted` с `await` (ждём `flushPromises` или `findBy`).

## Вопрос

Как тестировать Vue-компонент, который обновляется после запроса или таймера? Чем отличаются `nextTick`, `flushPromises` и `waitFor`?

## Основная идея

Vue не обновляет DOM синхронно: изменения реактивного состояния накапливаются и применяются в следующем микротаске. Поэтому сразу после `count.value++` DOM ещё старый.

| Утилита | Что ждёт | Когда использовать |
| --- | --- | --- |
| `await nextTick()` | один цикл обновления DOM | после прямого изменения состояния (store, `ref` в тесте) |
| `await fireEvent.*` / `await wrapper.trigger()` | событие + `nextTick` | после действия пользователя |
| `await flushPromises()` | все уже разрешённые промисы | после замоканного запроса в `onMounted` или в обработчике |
| `await screen.findBy...` | появление элемента (опрос до таймаута) | данные, которые появятся позже |
| `await waitFor(() => expect(...))` | выполнение любой проверки | вызовы функций, произвольные условия |
| `await waitForElementToBeRemoved(...)` | исчезновение элемента | спиннер, toast |

`flushPromises` экспортируется из `@vue/test-utils`. Он не ждёт таймеры и реальную сеть — только промисы, которые уже готовы разрешиться. С MSW или `vi.fn().mockResolvedValue()` этого обычно достаточно, но `findBy` надёжнее: он повторяет проверку, пока результат не появится.

`waitFor` вызывает колбэк каждые 50 мс (по умолчанию) и при изменениях DOM, пока он не перестанет бросать ошибку. Через 1000 мс тест падает с последней ошибкой.

Правила для `waitFor`:

- внутри — только проверка, **без побочных эффектов**: кликов, вызовов функций. Колбэк выполняется много раз;
- одна проверка на `waitFor`: тогда понятно, чего ждём, и падение быстрее;
- не пустой колбэк: `await waitFor(() => {})` ничего не ждёт осмысленно.

**Асинхронный `setup`.** Компонент с top-level `await` в `<script setup>` становится асинхронным и рендерится только внутри `<Suspense>`. В тесте его оборачивают во вспомогательный компонент с `<Suspense>` и ждут через `flushPromises` или `findBy`.

## Пример

```ts
import { render, screen, waitFor } from '@testing-library/vue';
import userEvent from '@testing-library/user-event';
import ProfileForm from './ProfileForm.vue';

it('сохраняет профиль и показывает уведомление', async () => {
  const user = userEvent.setup();
  render(ProfileForm);

  await user.type(screen.getByLabelText('Имя'), 'Анна');
  await user.click(screen.getByRole('button', { name: 'Сохранить' }));

  // кнопка блокируется на время запроса
  expect(screen.getByRole('button', { name: 'Сохранение...' })).toBeDisabled();

  // ждём результат
  expect(await screen.findByRole('status')).toHaveTextContent('Профиль сохранён');
  expect(screen.getByRole('button', { name: 'Сохранить' })).toBeEnabled();
});

it('отправляет событие saved после сохранения', async () => {
  const user = userEvent.setup();
  const { emitted } = render(ProfileForm);

  await user.click(screen.getByRole('button', { name: 'Сохранить' }));

  await waitFor(() => expect(emitted()).toHaveProperty('saved'));
});
```

То же на Vue Test Utils через `flushPromises`:

```ts
import { mount, flushPromises } from '@vue/test-utils';
import { getUsers } from '@/api/users';
import UserList from './UserList.vue';

vi.mock('@/api/users');

it('показывает пользователей после загрузки', async () => {
  vi.mocked(getUsers).mockResolvedValue([{ id: 1, name: 'Анна' }]);
  const wrapper = mount(UserList);

  expect(wrapper.text()).toContain('Загрузка...');

  await flushPromises(); // промис из onMounted разрешился, DOM обновлён

  expect(wrapper.findAll('li')).toHaveLength(1);
  expect(wrapper.text()).toContain('Анна');
});
```

Плохие варианты:

```ts
// побочный эффект внутри waitFor — клик повторится много раз
await waitFor(() => {
  fireEvent.click(button);
  expect(screen.getByText('Готово')).toBeInTheDocument();
});

// забыт await — проверка выполняется до ререндера
wrapper.find('button').trigger('click');
expect(wrapper.text()).toContain('1');

// ручное ожидание
await new Promise((r) => setTimeout(r, 500));
```

## Что важно помнить

- Сеть в тестах мокается (MSW), поэтому ответы приходят быстро и таймауты по умолчанию достаточны.
- `nextTick` ждёт только ререндер, но не промисы: для запросов нужен `flushPromises` или `findBy`.
- Проверка промежуточного состояния (loading) делается сразу после `await` действия, до `flushPromises`.
- Для таймеров (`setTimeout`, debounce) используйте fake timers: `vi.advanceTimersByTime(300)`, затем `await nextTick()`.
- Если `findBy` падает по таймауту, проверьте `screen.debug()` — возможно, запрос упал с ошибкой.

## Мини-шпаргалка

Изменил состояние → `await nextTick()`. Действие → `await fireEvent` / `await trigger`. Запрос → `await flushPromises()` или `await findBy`. Условие → `await waitFor(() => expect(...))` без побочных эффектов. Исчезнет → `waitForElementToBeRemoved`.
