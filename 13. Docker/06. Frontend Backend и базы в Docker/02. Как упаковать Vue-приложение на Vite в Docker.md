# Как упаковать Vue-приложение на Vite в Docker

> [!NOTE]
> Vue SPA на Vite в production — это статические файлы. Образ собирают в два stage: **Node.js** выполняет `npm run build`, **Nginx** раздаёт `dist`. Для Vue Router в режиме `createWebHistory()` нужен fallback на `index.html` (`try_files`), для ассетов с хэшем в имени — долгий кэш. Переменные `VITE_*` вшиваются в бандл **при сборке** и видны любому пользователю — секретов там быть не может, а для смены API-адреса без пересборки нужна runtime-конфигурация.

## Вопрос

Как упаковать Vue-приложение на Vite в Docker для production и для разработки?

## Production Dockerfile

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
ARG VITE_API_URL=/api
ENV VITE_API_URL=${VITE_API_URL}
# build-only — без vue-tsc: проверку типов делают в CI до сборки образа
RUN npm run build-only

FROM nginx:1.29-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

`CMD` указывать не нужно: базовый образ Nginx уже запускает `nginx -g "daemon off;"`.

В шаблоне `create-vue` скрипт `build` параллельно запускает `vue-tsc` и `vite build`. В Dockerfile часто вызывают `build-only`, чтобы не тратить время на проверку типов, которую уже прошел CI, — или оставляют `build`, если образ собирается без отдельного CI.

## nginx.conf для SPA

```nginx
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  # хэшированные ассеты можно кэшировать «навсегда»
  location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  # index.html не кэшировать, чтобы пользователи получали новую версию
  location = /index.html {
    add_header Cache-Control "no-cache";
  }

  # Vue Router (createWebHistory): /profile/42 → index.html
  location / {
    try_files $uri $uri/ /index.html;
  }

  gzip on;
  gzip_types text/css application/javascript application/json image/svg+xml;
}
```

Без `try_files` прямой переход или обновление страницы `/profile/42` вернёт 404. С `createWebHashHistory()` (адреса вида `/#/profile/42`) fallback не нужен, но такие URL хуже для SEO и выглядят непривычно. Страницу 404 в этом случае показывает сам Vue Router через маршрут `/:pathMatch(.*)*`.

Если приложение отдаётся не из корня (`/app/`), путь задают в двух местах: `base: "/app/"` в `vite.config.ts` и `createWebHistory(import.meta.env.BASE_URL)` в роутере — плюс соответствующий `location` в Nginx.

## Проксирование API

Чтобы не настраивать CORS, Nginx может проксировать запросы на backend в той же Docker-сети:

```nginx
location /api/ {
  proxy_pass http://api:3000/;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

Тогда фронтенд обращается к относительному `/api`, и один образ работает в любом окружении.

## Переменные окружения: build-time и runtime

`import.meta.env.VITE_API_URL` заменяется строкой при `vite build`. Поменять значение через `docker run -e` после сборки **нельзя**. Варианты:

1. Собирать отдельный образ на окружение через `--build-arg` — просто, но нарушает принцип «собрать один раз».
2. Использовать относительные адреса (`/api`) и прокси — чаще всего лучший вариант.
3. Генерировать `config.js` при старте контейнера:

```sh
# /docker-entrypoint.d/40-config.sh — официальный образ nginx выполняет такие скрипты перед стартом
cat > /usr/share/nginx/html/config.js <<EOF
window.__CONFIG__ = { apiUrl: "${API_URL}" };
EOF
```

```html
<!-- index.html, до скрипта приложения -->
<script src="/config.js"></script>
```

```ts
// src/config.ts
declare global {
  interface Window { __CONFIG__?: { apiUrl: string } }
}

export const config = {
  apiUrl: window.__CONFIG__?.apiUrl ?? import.meta.env.VITE_API_URL,
};
```

## Разработка

```yaml
services:
  web:
    image: node:24-alpine
    working_dir: /app
    command: sh -c "npm ci && npm run dev -- --host 0.0.0.0"
    ports: ["5173:5173"]
    volumes:
      - .:/app
      - /app/node_modules
```

`--host 0.0.0.0` нужен, чтобы dev-сервер принимал подключения извне контейнера. То же можно задать в `vite.config.ts`: `server: { host: true }`. Если HMR не срабатывает на macOS или Windows, включите `server.watch.usePolling` или используйте `compose watch`. Если страница открыта через другой порт или прокси, WebSocket HMR настраивают через `server.hmr.clientPort`.

## Частые ошибки

- Запускать `vite dev` или `vite preview` как production-сервер.
- Забыть SPA fallback для `createWebHistory`.
- Положить секрет в `VITE_*`.
- Ожидать, что `-e VITE_API_URL` изменит уже собранный бандл.
- Кэшировать `index.html` надолго — пользователи застревают на старой версии.

## Что важно помнить

- Node.js нужен только на этапе сборки: финальный образ Nginx весит десятки мегабайт.
- Всё, что попало в бандл, публично.
- Один образ на все окружения достигается относительными адресами или runtime-конфигом.

## Мини-шпаргалка

- `node` build → `nginx` runtime.
- `try_files $uri $uri/ /index.html`.
- `/assets/` — `immutable`, `index.html` — `no-cache`.
- `VITE_*` — build-time и публичны.
- Dev: `--host 0.0.0.0` или `server.host: true`.
