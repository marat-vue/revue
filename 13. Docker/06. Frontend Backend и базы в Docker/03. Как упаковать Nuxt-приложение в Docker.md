# Как упаковать Nuxt-приложение в Docker

> [!NOTE]
> Nuxt с SSR и серверными маршрутами (`server/api`) — это **Node.js-сервер Nitro**, а не статика. `nuxt build` собирает самодостаточный каталог `.output`: сервер `.output/server/index.mjs` вместе с нужными зависимостями и клиентские ассеты в `.output/public`. Поэтому `node_modules` в финальный образ не копируют: в последний stage кладут только `.output`, задают `HOST=0.0.0.0` и запускают `node .output/server/index.mjs`. Значения `runtimeConfig` можно переопределять при запуске через переменные `NUXT_*` и `NUXT_PUBLIC_*`, поэтому один образ работает в любом окружении.

## Вопрос

Как упаковать Nuxt-приложение в Docker? Чем SSR-сборка отличается от статической (`nuxt generate`)?

## Что лежит в .output

```text
.output/
  nitro.json
  public/              ← клиентские ассеты (_nuxt/*.js, *.css, файлы из public/)
  server/
    index.mjs          ← точка входа сервера
    chunks/            ← серверный код страниц и API
    node_modules/      ← только используемые зависимости (трассировка Nitro)
```

Nitro трассирует импорты и копирует в `.output/server/node_modules` только нужные файлы. Образ получается в несколько раз меньше, чем при копировании всех зависимостей.

## Production Dockerfile

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS base
WORKDIR /app

FROM base AS deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NUXT_TELEMETRY_DISABLED=1
RUN npm run build

FROM base AS runner
ENV NODE_ENV=production \
    HOST=0.0.0.0 \
    PORT=3000
COPY --from=build --chown=node:node /app/.output ./.output
USER node
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

`npm ci` в `deps` также запускает `postinstall: nuxt prepare` из шаблона — он генерирует типы в `.nuxt`. Если в `deps` ещё нет исходников, этот шаг можно пропустить флагом `--ignore-scripts`: `nuxt build` всё равно подготовит проект.

## runtimeConfig: build-time и runtime

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    databaseUrl: "",                // только сервер: NUXT_DATABASE_URL
    authSecret: "",                 // только сервер: NUXT_AUTH_SECRET
    public: {
      apiBase: "/api",              // сервер и браузер: NUXT_PUBLIC_API_BASE
    },
  },
});
```

| Источник | Когда читается | Где видно |
| --- | --- | --- |
| `runtimeConfig.public` + `NUXT_PUBLIC_*` при запуске | При старте сервера, передаётся клиенту в payload страницы | В браузере — публично |
| `runtimeConfig` (не public) + `NUXT_*` при запуске | При старте сервера | Только на сервере (`server/`, `useRuntimeConfig()` на сервере) |
| `import.meta.env.*`, `process.env.*` в коде приложения | При `nuxt build`, вшивается в бандл | Зависит от места использования |

```bash
docker build -t web .
docker run -e NUXT_DATABASE_URL=postgres://... -e NUXT_AUTH_SECRET=... \
  -e NUXT_PUBLIC_API_BASE=https://api.example.com -p 3000:3000 web
```

Главное отличие от SPA на Vite: публичные значения из `runtimeConfig.public` можно менять при запуске контейнера без пересборки, потому что сервер передаёт их клиенту вместе с HTML. Но переменные нужно **объявить** в `runtimeConfig` (хотя бы пустой строкой) — Nuxt подставляет только известные ключи.

Нюанс: страницы, пререндеренные при сборке (`routeRules: { "/": { prerender: true } }`), тоже «запекают» значения на момент сборки.

## Кэш и несколько реплик

Nitro хранит кэш `routeRules` (`swr`, `isr`), `cachedEventHandler` и `useStorage()` по умолчанию в памяти процесса. При нескольких репликах у каждой свой кэш, и инвалидация в одной не затрагивает остальные. Для горизонтального масштабирования подключают общий storage-драйвер (например, Redis) в `nitro.storage` или используют платформу с поддержкой Nitro.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    storage: {
      cache: { driver: "redis", url: process.env.REDIS_URL },
    },
  },
});
```

## Изображения

Модуль Nuxt Image с провайдером `ipx` оптимизирует картинки на сервере через `sharp` — на Alpine его сборку стоит проверить. Если изображения отдаёт CDN (Cloudinary, imgproxy), `sharp` в образе не нужен.

## Статический Nuxt

Если SSR не нужен, `nuxt generate` пререндерит все страницы в `.output/public`. Такой сайт упаковывают как Vue SPA — в Nginx:

```dockerfile
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npx nuxi generate

FROM nginx:1.29-alpine
COPY --from=build /app/.output/public /usr/share/nginx/html
EXPOSE 80
```

Серверные маршруты `server/api` при этом не работают, а `runtimeConfig` фиксируется при генерации.

## Compose

```yaml
services:
  web:
    build: .
    ports: ["3000:3000"]
    environment:
      NUXT_DATABASE_URL: postgres://app:secret@db:5432/app
      NUXT_PUBLIC_API_BASE: /api
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```

Если при сборке пререндерятся страницы с данными из БД или API, источник должен быть доступен во время `nuxt build` — это частая причина падений в CI. Обычно такие страницы оставляют SSR с кэшем (`swr`) вместо `prerender`.

## Частые ошибки

- Раздавать SSR-приложение как статику через Nginx.
- Копировать в финальный образ весь проект и `node_modules` вместо одного `.output`.
- Не задать `HOST=0.0.0.0` — сервер недоступен снаружи контейнера.
- Положить секреты в `runtimeConfig.public`.
- Передать `NUXT_PUBLIC_FOO`, не объявив `foo` в `runtimeConfig.public`, — значение не появится.
- Запускать `nuxt dev` или `nuxt preview` как production-сервер.

## Что важно помнить

- `nuxt build` → самодостаточный `.output`; в образ копируют только его.
- `runtimeConfig` + `NUXT_*` дают runtime-конфигурацию: собрать один раз, запускать везде.
- Чисто статический сайт (`nuxt generate`) упаковывают как SPA — в Nginx.
- При нескольких репликах кэш Nitro нужно делать общим.

## Мини-шпаргалка

- `nuxt build` → `.output`, `CMD ["node", ".output/server/index.mjs"]`.
- `HOST=0.0.0.0`, `PORT=3000`.
- `NUXT_*` — серверные, `NUXT_PUBLIC_*` — публичные, оба переопределяются при запуске.
- `nuxt generate` → `.output/public` → Nginx.
